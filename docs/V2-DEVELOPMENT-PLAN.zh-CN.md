## 3. 已购状态的产品规则

### 3.1 三个数量分开表达

- 总需求：当前所有已选菜谱的食材需求之和。
- 应采购：`max(总需求 − 库存, 0)`，仍只扣一次库存。
- 未勾选项：应采购清单中尚未标记已购的条目。

例如番茄总需求 4、库存 1，应采购 3。勾选“已购 3 个”后，该行进入已购分组，未勾选条目数减少，但库存仍为 1，应采购量仍为 3；菜谱不能因此变成“库存齐全”。页面显示“采购已完成，库存尚未更新”等清晰状态。

本轮只支持整行勾选和撤销，不做部分购买数量、自动入库或自动扣库存。用户需要更新库存时，通过既有库存表单显式保存总量；不会在点勾选时暗中加 3。

### 3.2 清单变化后的标记

以 `(workspace, ingredientId, unit, 当前应采购数量)` 判定标记是否仍适用：

| 变化 | 标记处理 |
| --- | --- |
| 刷新、重启、无关食材变化 | 当前单位与应采购量没变，保留标记 |
| 添加/移除菜谱或修改库存后，应采购量改变 | 该行取消已购，提示数量已变化需重新确认 |
| 应采购量归零或该食材不再需要 | 删除旧标记；以后重新出现时默认未购 |
| 食材单位改变或进入单位待核对状态 | 相关标记清除；不展示不完整的采购总计 |
| 清空所有菜谱 | 清空选择与已购标记，库存不变 |
| 目录仅调整文案/热量，采购量未变 | 保留标记；不因全局目录版本变化一律清空 |

这是一份当前购物任务的勾选状态，不是消费记录或采购流水。若以后需要部分购买、价格和历史订单，应另行设计数据模型。

## 4. 食材分类、两种推荐与检索

### 4.1 数据库区分食材和调料

规范原料表增加 `kind = food | seasoning`，界面对应“食材/调料”分组，沿用规范 ID 和库存单位，不拆成两套重复 ID 的库存表。每条菜谱用料增加 `role = food | seasoning`，默认继承原料分类，允许经过审核的菜谱级覆盖。例如蒜作为少量调味和蒜作为主要食材，角色可能不同；不能仅按名称一刀切。每道有效菜必须至少有一种主食材。

“调料”与“可选”是两回事。必需油、盐、酱油等仍参与完整可做性、缺料和采购数量；不默认用户拥有全部调料。分类迁移不改变旧库存、数量、单位和选择。水、可选点缀沿用明确的配方规则，不借分类改掉既有数量语义。

### 4.2 基于已有食材的推荐

候选菜必须至少命中一种库存数量大于零的必需主食材；调料不参与候选生成、覆盖率和排序。只有调料或库存为空时，展示“暂无主食材匹配”，提供录入库存、浏览全部和每日灵感入口。

对每道候选按不同主食材 ID 计算：主食材总数、已拥有种类数、数量足够种类数、完全缺少种类数、数量不足种类数和单位待核对项。同 ID 在菜谱中重复出现时先按单位合并需求，不能重复计分。

- **主食材齐全：** 所有必需主食材数量足够且单位可比较。缺调料仍可在本组推荐，但必须提示“主食材齐全，仍缺调料”，不能标为“全部用料足够”。
- **部分匹配：** 至少拥有一种主食材，但其他主食材缺少或数量不足。显示“已有 X/Y 种主食材”及具体数量缺口。
- **单位待核对：** 有同名规范食材，但单位无法比较。可以显示候选与待核对原因，不能当作数量足够。

排序先主食材齐全，再部分匹配，再含单位待核对的候选；组内依次按数量足够种类占比、已拥有种类占比降序，完全缺少种类数升序，最后稳定 recipe ID。待核对标志优先决定分组。所有比例只基于主食材，不混加 g、ml、piece，也不将比例称为营养适配或算法准确率。

独立的“全部用料足够/缺料/单位待核对”状态仍使用全部必需用料计算。菜谱详情、逐菜缺口和多菜合并清单继续复用 V1 规则，推荐评分不改采购算法。

### 4.3 每日灵感

每日灵感不以库存参与候选、抽样或排序。从符合当前检索条件的目录中确定性选择最多 3 道、不重复；依据服务端 `Asia/Shanghai` 日期、目录版本和规范化后的筛选条件生成稳定结果。同日、同版本、同条件，即使增删库存，推荐菜 ID 也不变。

卡片可以附带当前真实可做性与缺口，但这些注释不反向改变当天选菜结果。空库存仍展示；候选不足 3 道显示实际数量，筛选无结果明确为空，读取失败显示重试。日期跨日、目录更新或筛选改变可产生新结果；不要求相邻两日完全无重复。

从灵感进入详情、加入购物清单使用既有多菜流程。运行时不依赖实时外部 API，不引入训练模型或未经验证的个性化。

### 4.4 Find recipes 筛选与交互

提供“全部菜谱 / 用现有食材 / 每日灵感”入口，共用以下可选筛选项：

| 维度 | 字段与例子 | 约定 |
| --- | --- | --- |
| 国家与地区菜系 | 国家，如中国、日本、韩国、意大利；地区，如川菜、粤菜、江浙菜 | 国家为上级、地区为下级；支持多归属、融合菜和明确的未归类，不强行标为正宗 |
| 口味 | 酸、甜、苦、辣、咸、鲜 | 多标签；酸甜可同时标酸和甜；不为填选项随意给菜贴“苦”标签 |
| 餐次 | 早餐、午餐、晚餐 | 多标签，一道菜可适合多个餐次；零食/加餐留作后续扩展 |
| 关键词 | 中英文菜名、规范食材名 | 去除首尾空格，保留现有中英文检索能力 |
| 完整可做性 | 全部用料足够、缺料、单位待核对 | 保留既有能力；使用全用料规则，不等同推荐的主食材覆盖率 |

每一项均可不选。只选一个口味、只选一个地区或只输入关键词都能查询；填满全部条件也能查询。同一维度多选取 OR，不同维度取 AND。例如“日本或韩国”且“辣或酸”且“晚餐”，结果必须同时满足三个维度。筛选值顺序不影响结果。

地区可单独选，服务端能解析所属国家；显式传入相互矛盾的国家/地区组合返回明确的 400 错误。界面切换国家时清理不兼容地区并给出提示，不能留下看不见的冲突条件。零结果显示当前条件及清除入口，不偷偷放宽条件；“苦”等暂时无菜可匹配的选项可显示计数 0。

筛选通过 URL query 保存；进入详情再返回、刷新和分享本机地址保留条件，返回尽量恢复列表位置。明确“清除筛选”只改变检索状态，不清库存与购物清单。每页默认 20 道，返回总数、页码；条件变化回第一页，稳定排序，空页与页数变化有明确处理。移动端筛选可展开/收起，已选条件和结果数可见。

建议的数据选取配额如下，作为调查起点，可依据合法来源和人工审核调整；最终总数仍须为 100，不把配额当作已经取得的菜谱：

| 类别 | 目标数量 |
| --- | ---: |
| 中国地方菜 | 38 |
| 日本 | 12 |
| 韩国 | 10 |
| 东南亚 | 12 |
| 意大利 | 10 |
| 法国 | 4 |
| 其他欧美菜 | 6 |
| 南亚 | 6 |
| 原 V0 演示配方 | 2 |
| 合计 | 100 |

所有常规菜谱都有经审核的国家/地区、至少一个口味和一个餐次；演示、融合及来源不明的地域信息明确表达。口味与餐次允许多标签，无须均匀分布，不能为满足配额编造用料或文化归属。

延续现有 HowToCook 来源、许可和快照流程；其他国家菜谱另行筛选可复用来源。每个新来源在导入前核对实际许可、再分发及改编条件，保留原链接、版本、许可文件、原始快照和修改说明。仅公开可读不代表可整库复制；不默认单一中文菜谱库覆盖所有国家。

每道菜须核验规范原料 ID、food/seasoning 角色、可计算用量与单位、基础份数、步骤、时长、分类、来源及图片。“适量”若需要规范化，须有明确审核记录；不从模糊描述推断精确重量后假装原文提供。新增食材补齐规范单位，避免葱/香葱等别名形成重复库存。

图片复用原 20 张，新 80 道按每批 10–20 道制作与审核；使用独立生成的图片或已核验可复用素材，不能盗链网站原图。记录提示词/素材许可、生成或获取时间、菜谱 ID、替代文字及审核结果；检查图像与配方食材、烹饪方式一致。新图压缩为最长边约 900px 的 JPG，列表懒加载，避免把生成原图全部打进仓库。占位图和待审核草稿不计入 100 道交付。

按 40 → 70 → 100 道分批合入和核对；每批验证 ID 唯一、分类、来源、图片存在及用量合法。现有 seed 的 20 道上限需要受控调整到 100，区分历史测试夹具与生产目录断言。目录升级不得删除已有选择、重置库存或改变原 V0 夹具数量。

## 5. 热量数据与计算

### 5.1 来源与核验

优先调查 USDA FoodData Central 的匹配条目与产品包装营养标签。FDC 官方说明其数据采用 CC0，要求 API 请求携带密钥；本项目优先在准备阶段取得所需数据并保存来源快照，运行时从本地已核验数据读取，不强制每次打开页面访问外网。[数据说明](https://fdc.nal.usda.gov/data-documentation/)、[API 与许可说明](https://fdc.nal.usda.gov/api-guide/)。

现有 HowToCook 原文中的热量数字不直接复用：本项目调整过用量、份数和部分原料，它们不必然对应当前菜谱。任何展示值都需要对应当前配方和可追溯输入。

每个营养映射记录 ingredientId、食物条目 ID/名称、原料或熟制状态、能量单位、基准质量/体积、来源链接、数据日期/版本与核对人。品牌食品不能随意用另一品牌的数值冒充同一产品。

### 5.2 单位与缺失规则

- g 原料使用明确的按质量数据；ml 原料须有对应按体积数据或有来源的密度；piece 原料须有有来源的单件可食重量。
- 营养估算用的单件重量或密度只作用于营养计算，不改变库存匹配的单位规则，不让 g 与 piece 自动互换。
- 生米与熟米饭分别匹配；带壳虾、整鱼、鸡翅要明确可食部、骨/壳处理。盐水丢弃、油残留和汤汁等差异记录为估算假设，不能声称实测精度。
- 任一必需原料缺少可信映射或换算，整道菜显示“热量不可用”，不能省掉该原料再给一个完整总量。份数缺失或无效时，每份不可用；未知值不用 0 替代。
- 不在本轮加入营养目标、饮食诊断、蛋白质/碳水等完整营养面板。

### 5.3 输出与覆盖率

`整道菜 kcal = Σ(当前配方各原料能量)`；`每份 kcal = 整道菜 kcal / 基础份数`。底层保留精度，显示时统一取整，并保留原始计算值以供复核。600 kcal、3 份的验收夹具显示每份 200 kcal；这是数学测试数据，不是某道菜的营养事实。

逐道审查全部 100 道菜，均明确为“有来源的估算”或“不可用及原因”。本轮最低可用性目标调整为至少 20 道完整估算，优先选择用量可核对的菜谱；其他菜如数据不全，明确不可用，不为了凑覆盖率编值。若不足 20 道，E2 保持未验收，记录补数据或延期决定；100 菜目录目标不等于 100 菜营养估算均已完成。

详情页展示基础份数、整道菜/每份 kcal、估算标识、来源入口和关键假设；列表仅显示简短每份估算或不可用，不以热量影响“现在可做”的正确性。

## 6. 可选的配方倍数调整

这是本轮新增建议，原 E1–E4 不要求该功能。只有 P0/P1 稳定且有明确余量时再加入，不作为掩盖反馈或热量数据不足的替代交付。

采用整数倍数 `recipeMultiplier = 1–10`，默认 1。基础配方 2 人份，选择 2 倍即 4 人份，所有原料同步翻倍；piece 仍为整数。暂不支持任意分数倍，避免将半个鸡蛋强行向上取整后出现配方与热量不一致。

同一道菜保持一条选择，通过显式修改倍数增加需求；重复点“加入”不暗增倍数。缩放后先求各菜需求，再合计扣一次库存，随后重核已购状态。整道配方热量按倍数增加，每份热量保持基础估算。修改后刷新/重启保留。

此项会触及现有 validateItem 的数量上限与整数百分单位计算，必须检查缩放后范围和溢出边界，不能简单改变前端显示数字。

## 7. 数据迁移与持久化设计

沿用现有 Express、SQLite、版本化迁移和权威快照，不更换数据库或重建项目。

### 发现功能迁移：003_recipe_discovery.sql

增加 ingredients.kind、recipe_requirements.role；增加国家/地区及父级关系、口味、餐次字典和 recipe_cuisines / recipe_tastes / recipe_mealtimes 多对多关联。按菜谱和标签建立索引；使用绑定参数和白名单校验，不拼接用户 SQL。100 道规模先用简单查询，不提前引入搜索集群或向量库。

新旧原料分类需人工审核后回填；迁移与 seed 的顺序保证旧库可启动并保留选择，不依靠删库重建。扩充目录时增加 catalogVersion，保持规范 ID 稳定。100 道目录、来源清单和图片 manifest 可作为版本化文件，经 seed 同步数据库，不能由前端临时拼出另一份目录。

### 购物与营养迁移：004_v2_shopping_and_nutrition.sql

| 实体 | 关键字段与约束 | 用途 |
| --- | --- | --- |
| shopping_purchase_marks | workspace_id、ingredient_id、unit、marked_quantity_minor、purchased、updated_at；同空间同食材唯一 | 独立保存已购状态，绑定标记时的应采购量 |
| nutrition_sources | id、provider、external_id、url、retrieved_at、source_version、license、snapshot_path | 营养来源与快照索引 |
| ingredient_nutrition_profiles | ingredient_id、source_id、basis_unit、basis_quantity、energy_kcal、food_state、conversion_data、review_note | 明确基准与换算依据，不改变规范库存单位 |

每日灵感使用纯计算，不为每次 GET 写入日推荐表。基础份数继续使用现有菜谱 metadata；营养估算由服务端根据当前配方和来源计算，不让浏览器提交 kcal。

已购标记不直接附在被删除重建的 shopping_list_items 行上，也不对该派生行设置会造成标记反复消失的级联删除。重建合并清单时，在同一事务内按第 3 节规则协调 marks；孤立、过期标记清除。单菜参考仍是派生结果，不维护第二套手填采购数。

### 可选迁移：005_recipe_multiplier.sql

仅在实施第 6 节时向 shopping_selections 增加有约束的 multiplier，默认 1；已有选择全部保持一倍，顺序不变。不为尚未实施的可选功能预先改写旧需求量。

每次迁移前备份，在 schema 002 的真实格式副本上演练。001/002 保持不可变，校验和不改。升级后保留库存、所有选择、选择顺序与采购数量；重复迁移无变化。回退使用匹配的旧应用和升级前备份，不能删除新表后假称无损回退。

## 8. 服务接口与前端合同

现有库存、选择、移除、清空接口继续使用 expectedRevision，成功后返回完整权威快照。新增字段不由前端乐观推算覆盖服务器数据。

| 接口 | 请求/结果 | 约定 |
| --- | --- | --- |
| PUT /api/shopping-items/:ingredientId/purchased | purchased、expectedRevision | 只允许当前有效且单位可比较的正缺口行；服务端绑定当前单位和应采购量；可撤销；不能改库存 |
| GET /api/recipes | 可选 q、countries、regions、tastes、meals、availability、page、pageSize | 全部可单选或组合，返回结果、总数和规范化 appliedFilters |
| GET /api/recommendations/pantry | 相同筛选 + 主食材覆盖、排序原因、pantryRevision | 从当前空间的权威库存计算，不接受客户端伪造拥有量 |
| GET /api/inspiration | 相同筛选 + date、timezone、catalogVersion、recipeIds | 最多 3 道，库存不影响选菜；不改变 workspace revision |
| GET /api/snapshot | 原字段 + 当前清单 purchased/未勾选计数、必要营养状态 | 核心页面保持一致数据来源；列表接口复用相同的服务端规则 |
| PUT /api/shopping-selection/:recipeId/multiplier | multiplier、expectedRevision | 可选；只修改已选菜；事务重算需求和已购状态 |

营养概要随菜谱快照返回；来源明细可通过只读详情接口按需读取，避免把全部原始来源文件发给浏览器。三个只读发现接口共用筛选服务与分类字典；推荐额外返回主食材缺口与调料缺口，不能让浏览器另算不同排序。命名可在 Day 1 合同评审微调，状态码、字段类型、错误结构和缺失值语义必须冻结。

不存在的购物项返回 404；已过期 revision 返回 409；无效布尔值/倍数/单位返回 400 或 422 并保持错误结构一致；存储失败返回错误且事务回滚。勾选时另一标签页改了库存，必须先冲突并载入新总量，不能替新数量保留旧勾选。

购物页分“待购买/已购买”，可撤销，显示完成条目数；所有行勾完仍保留已选菜和总需求。页面明确说明已购不会自动入库。保存失败、超时后结果未确认、冲突、空列表和单位待核对继续遵循 V1 的草稿/重读规则。
