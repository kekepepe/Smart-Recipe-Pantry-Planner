# V1 多菜购物清单

日期：2026-11-07（Asia/Shanghai）。按用户最新要求，将原计划 V2 的多菜合并提前纳入 V1。仍在本机受控开发，不部署公网；后续 App 包装另行实施。

## 使用行为

从菜谱详情添加一道菜后，原有菜谱保留。清单包含两层：

- **Buy for all recipes**：先按规范食材与兼容单位累加所有已选菜的需求，再扣一次共享库存，采购量不小于零。
- **Your selected recipes**：保存每道菜，显示它单独使用当前库存时的缺口。这里的单菜参考不能直接相加；购买以合并总计为准。

例如 A、B 各需番茄 2 piece，库存 1 piece：单独做 A 缺 1，单独做 B 也缺 1；一起做总需求 4，扣库存 1，实际应买 3，不能把两份单菜缺口相加成 2。

同一道菜重复点击不会增加重复记录；目前按每道菜的固定配方做一次，不提供同菜多份数量调节。已够做的菜也可加入，因为多道菜一起做可能争用同一份库存。移除一道菜后立即重算，可确认清空所有选择；两种操作都不扣减库存。

库存修改后，逐菜明细与合并总计一起更新。无法比较的单位不猜测换算；合并状态为 Check units 时不输出一份看似完整但实际不完整的采购总量。

## 数据和事务

schemaVersion 从 1 升为 2；新增不可变迁移 `002_multiple_recipes.sql`，保留 001 原文与校验和。

- `shopping_selections` 以 `(workspace_id, recipe_id)` 唯一，保存有序的多菜选择。
- `shopping_lists` 保存整张合并清单的状态、库存版本和目录版本。
- `shopping_list_items` 保存合并后正缺口；选择和条目可由当前库存/目录重建。
- 单菜缺口由已保存选择和当前库存即时计算，不保留会失效的第二份计算缓存。

添加、移除、清空、库存更新与清单重算都在写事务内完成；revision 冲突保护、真实保存失败回滚及断连后同步规则继续生效。目录升级和修复工具对所有已选菜重算，不再只处理最后一道。

## API 与快照

保留 `PUT /api/shopping-selection`，语义改为加入/保留指定 recipeId，不再替换其他菜。

新增 `DELETE /api/shopping-selection/:recipeId` 移除单菜；`DELETE /api/shopping-selection` 清空选择。写入仍要求 expectedRevision。

快照提供：

- `shoppingRecipeIds`：有序 ID 数组。
- `shoppingRecipes`：逐菜参考评估。
- `shopping`：合并需求、总缺口、单位问题及状态；无已选菜时为 null。

旧的单值 shoppingRecipeId 被数组取代，升级服务后应刷新旧页面。

## 升级与数据保留

已有用户库先按旧版本备份，再停止服务，运行 `npm run db:migrate`，最后重新启动并刷新网页。正常迁移自动把旧单菜选择写入 shopping_selections，保留库存、原清单条目和目录。已初始化空间 revision 递增，防止旧快照覆盖新状态；重复迁移不再改数据。

本机实际升级前已做一致性备份；升级后与升级前保存的快照对照，库存、原选菜和原采购缺口一致。没有重置数据库，没有为了展示新页面自动给用户添加测试菜谱。旧备份仍按旧兼容版本恢复；需升级时对恢复副本应用迁移 002。

## 验证范围

新增规则测试覆盖：两菜各需 2、库存 1 合计买 3；单菜都可做但一起做仍需购买；小数；库存富余；不兼容单位；输入不变。

接口/数据库检查覆盖：追加、重复添加、移除、清空、库存更新、故障回滚、旧 schema 001 含选择数据迁移、重复迁移、文件重开和实际服务进程重启后多菜留存。

浏览器目标流程：两蛋一番茄 → 添加原番茄菜 → 返回再添加番茄炒蛋 → 两道菜都保留 → 总计缺番茄 3 → 刷新保持 → 移除一道变为缺 1 → 取消/确认清空。桌面 1440×1000 和手机 375×812；手机额外模拟第二道保存失败，再重试，确认第一道始终保留。使用项目 Playwright（Browser plugin not available）。

原有 45 项技术检查扩展为 55 项：25 项规则/状态、10 项 API、12 项集成、8 项浏览器；另有 demo 5 项断言。最终本机与远端执行结果以实际命令和当前提交 Actions 为准，不计为团队独立复现或真实用户试用。
