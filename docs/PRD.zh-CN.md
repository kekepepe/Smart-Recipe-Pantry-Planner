## 1. 用户想解决什么问题

下班回家，冰箱里有两个鸡蛋和一个番茄。用户想知道：“现在能做哪道菜？如果想做另一道，究竟还差多少？”普通菜谱能告诉人怎么做菜，却常把核对库存、计算缺口和抄购物清单留给用户。产品的首要目标是让这三个判断在同一次选菜过程中完成。

家庭烹饪者是主要用户；学生和忙碌上班族尤其需要减少录入和反复比对。关注饮食的用户还希望知道每份的大致热量，这是 V2 的需求。开发团队负责验证任务能否完成；运营维护者负责菜谱数据质量和故障处理。产品只生成清单，不处理下单、支付、配送，不训练专用 AI 模型，也不提供医学营养建议。

## 2. V0：先验证一次做饭决策

制作可点击的 Web 原型，用固定示例数据、可重置的会话状态串起以下页面。首页提供“使用示例库存”和“自己添加”两个入口；修改库存、返回列表和再次查看菜谱必须反映本次操作。原型可在本机演示，不要求账户、真实数据库或公网部署。

| 用户动作 | 页面必须回答的问题 | 验收示例 |
| --- | --- | --- |
| 在「我的食材」添加鸡蛋、番茄 | 添加成功了吗？数量和单位对吗？ | 两个鸡蛋、一个番茄显示在库存中；输错数量可直接修改，不必删除重录。 |
| 打开「找菜谱」 | 哪些现在能做？哪些差一点？ | 示例菜谱 A 需要两个鸡蛋，可归入“现在可做”；B 需要两个番茄，显示“差一个番茄”。分组有文字，不只用颜色。 |
| 进入 B 的详情 | 为什么推荐这道菜？还缺什么？ | 同屏比较“需要 2 个／已有 1 个／还差 1 个”，再查看步骤；返回保留筛选和库存。 |
| 把 B 的缺口加入「购物清单」 | 应买多少？刚才加成功了吗？ | 清单只有一个番茄；重复点击不翻倍。把库存改为两个番茄后，重新匹配时 B 进入“现在可做”。 |

空库存允许继续浏览菜谱，并解释如何开始匹配。没有可做菜谱时仍显示“补齐后可做”；都不缺时说明“无需购买”。数量无效时在字段旁说明原因，保留其他输入。小屏和键盘操作均能走完整条路径，按钮用动作命名，例如“把缺少的食材加入清单”。

## 3. V1：能在真实库存上完成的任务

| 需求 | 行为与通过条件 |
| --- | --- |
| P1 库存 | 拒绝负数数量。可新增、查看、编辑、删除食材和数量。保存后刷新页面或重启服务，结果仍在。删除前确认或提供撤销；写入失败不能提示已保存。 |
| P2 菜谱 | 每道菜列出所需食材、数量、单位和制作步骤。详情返回原列表位置；库存变化后重新判断，不显示过期结果。 |
| P3 匹配 | 按规范食材标识比对。同单位缺口 = max(所需量 − 已有量, 0)；所有必需食材缺口为零才标“现在可做”。仅换算已定义的兼容单位；无法比较时提示“请核对单位”，不猜测克与个之间的关系。 |
| P4 购物清单 | 保存的清单刷新和重启后仍保留；同一道菜重复添加不翻倍，食材齐全时明确无需采购。用户从一道菜的详情生成缺口清单，显示食材、缺少的数量和单位；再次生成该菜的清单时按最新库存更新。生成清单不会扣减库存。保存失败保留当前选择，可重试。 |

**V1 交付条件：** 在独立测试数据上执行 V0 示例、空库存、数量不足、单位不兼容、写入失败和重启恢复场景。每个场景留下预期、实际结果与缺陷记录。阻断核心任务的缺陷修复后再邀请试用。

## 4. V2：扩展选择，维持核心流程

| 需求 | 用户体验与验收 |
| --- | --- |
| E1 每日推荐 | 单独标明“每日灵感”，即使库存为空也有推荐。进入详情后再提示是否需采购，避免用户把推荐误认为现在可做。 |
| E2 热量 | 显示整道菜及每份的估算值，说明份数、数据来源和估算性质。若总量为 600 kcal、共 3 份，则每份为 200 kcal；若份数或数据缺失，显示“不可用”，不用零代替未知值。 |
| E3 多菜采购 | 对所选菜谱按食材汇总总需求，再扣一次库存。两道菜各需两个番茄，库存一个，应买三个。可勾选及撤销“已购买”，刷新后仍保留；勾选不自动增加库存。 |
| E4 反馈改进 | 依据 V1 试用记录优先改善易误解的匹配结果、筛选或操作。交付时重跑 P1–P4 并展示至少一项反馈如何被验证。临期提醒仅在核心功能稳定且有余力时考虑。 |

V2 之后可考虑手机 App，沿用已验证的数据和服务接口。V0–V2 可在手机浏览器试用，不包含原生 App、应用商店发布或推送通知。

## 5. 如何决定进入下一版

沿用 planning 的迭代增量开发：V0 验证用户是否看懂；V1 验证真实数据能否可靠保存；试用反馈决定 V2 的优先级。建议每轮邀请 5 位目标用户，各自从同一示例开始。给任务不给操作步骤：“用手边食材选一道能做的菜，再为另一道列出要买的东西。”主持人记录是否独立完成、首次卡住的页面、是否误判可做性，以及清单数量是否准确。记录匿名结果，避免只收满意度评分。

建议门槛：至少 4/5 无提示完成全流程，且没有将食材不足的菜误标为可做、清单算错或丢失已保存库存的已知缺陷。样本不足时报告实际人数与限制。V0 未达标先修改页面并复测；V1 将反馈按“阻断／易误解／便利性”排序；V2 复测原任务并增加每日推荐、每份热量和合并采购任务。

## 6. 数据、部署与持续运行

初始部署目标是受控本地演示。采用单一应用服务和一个持久化数据库；校验与计算由服务统一负责，浏览器不直接连接数据库。第 1 天检查 V0 后确定兼容技术栈。菜谱与热量采用小型人工核验数据集，记录来源与使用许可，演示不依赖实时外部 API。下述托管运行要求仅在开展共享试运行时启用。

| 阶段 | 实施要求与可验证结果 |
| --- | --- |
| V0 本地原型 | 使用可重置样例，无真实个人数据。另一名成员在干净环境按说明启动，完成一次演示并重置。记录哪些结果为模拟数据。 |
| V1 本地开发 | 界面通过应用服务读写数据库。区分规范食材、库存条目（所属空间、食材、数量、单位）、菜谱及其配料、购物清单及条目。使用版本化建表与迁移脚本、独立的开发和测试数据库；示例初始化不得覆盖已有记录。 |
| 本地验证后的有条件共享试运行 | 本地仍是主要开发环境。Mac mini 适合团队能负责供电、网络和重启恢复时使用；否则选有持续预算和维护负责人的云主机。上线前登记主机、负责人、访问地址和运行时段，配置 HTTPS、持久化存储及服务自启动。数据库不直接暴露公网，凭据不入库。 |
| 多人试用 | 给每个试用者独立空间与访问凭据；服务端验证资源归属。用两组凭据验证彼此不能读写库存与清单。若隔离尚未验证，只做单人受控演示。 |
| 持续服务 | 指定值班负责人和替补，检查服务及数据库健康状态并记录错误。建议每日备份到独立存储、发布前额外备份；在隔离环境完成恢复演练。模拟主机重启，确认服务自动恢复且库存和清单仍在。故障时通知试用者，按手册恢复上一个兼容版本。 |
| V2 发布 | 增加食谱份数、热量来源和已购状态。用测试数据库副本演练迁移与回退，验证旧库存和清单；记录发布版本、恢复步骤和回归结果。 |

启动试运行前仍需团队确定：技术栈和数据库、菜谱及热量数据的使用许可、主机和经费、备份保留期、维护时段与联系人。部署人员要能按手册在另一台机器恢复服务；仅在开发者电脑上能启动，不视作试运行就绪。
