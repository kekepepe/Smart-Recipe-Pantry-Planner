#### 离线安装与发布验收

1. **开工时验证打包路径。** 使用现有前端、Express、SQLite 和数据迁移机制。安装包包含运行时、原生 SQLite 依赖、构建后的前端、目录、图片和种子数据。通过系统应用入口启动并自动初始化本地数据库。用户无需另装 Node.js、运行 npm、手工启动服务或连接云服务。桌面封装和支持的系统及架构由 Peng 按实际构建、签名条件和可用测试设备确认。
2. **功能开发期间试装。** Peng 先以共享基线打出两平台候选包，Mao 和 Hao 在各自平台验证安装与启动，再随所选功能更新并复测。数据库放在用户可写的数据目录，应用更新时保留已有库存、选菜和购物清单。验证旧版本数据迁移、重启保留和备份恢复。
3. **迭代结束前验收候选包。** Mao 在干净的 macOS 环境、Hao 在干净的 Windows 环境分别下载对应候选包，断开网络，再执行安装、首次启动、浏览带图菜谱、库存录入、匹配、组合筛选、多菜采购、已购验证（如已纳入）和重启后的数据核对。测试要覆盖第二轮实际纳入的全部功能。安装和启动按标准系统流程验证，若有签名提示，记录实际行为及可行的安装步骤。
4. **迭代结束前完成正式发布。** 两平台候选包验收通过后，Peng 在同一固定提交对应的 GitHub Release 中上传两平台已验收的安装包和 SHA-256 校验值。发布说明标明支持的系统和架构、下载与安装步骤、本地数据位置、升级方式和已知限制。Mao 和 Hao 分别核对 macOS、Windows 正式下载文件与已验收包一致，Mao 验证老师的仓库访问权限。任一平台缺包、下载失败或离线主流程失败，第二轮发布项保持未完成。

### 10.3 PR 从开始到关闭

1. **开工前**在 Issue 写清交付范围、验收条件、依赖、被测版本和负责人。先确认共享文件归属。发现独立缺陷就另开 Issue；同一功能的评审修正留在原 PR。
2. **需要提早确认接口或共享文件时**开 Draft PR，关联 Issue、写出需要谁确认什么。依赖未合并时可以准备分支和测试，在转 Ready 前更新到实际目标基线并跑相关检查。
3. **有可验收的改动时**转 Ready，填写 `Closes #实际Issue号`（若 PR 只完成部分则用 `Refs #实际Issue号`）、变更内容、测试命令与结果、被测 SHA、未覆盖项及适用的 AI 和来源记录。显式 Request Review 给表中审批人。修复 PR 的主审为：Peng 的改动由 ChangPeng 审；ChangPeng 的规则改动由 Peng 审，涉及事务时 Hao 也审批；Hao 的改动由 ChangPeng 审；Mao 的验收或流程记录由 Hao 审，涉及产品范围时 Peng 也审批。
4. **审批后由作者本人合并。** 作者开工前确认自己有目标分支的合并权限。缺权限或遇到分支限制时，在关联 Issue 标明阻塞，由 Peng 协助核对仓库权限和分支规则，恢复后仍由作者本人合并。集成协调者和评审人可以复核条件，合并操作始终留给作者。指定评审人缺席时，在 Issue 记录改派和原因，由符合条件的另一位非作者审批。作者有实质改动时，请审批人在当前 head 重新审核，等所需审批与 CI 都通过再点击 Merge。共同编写的内容按各人能独立验收的改动拆 PR，分别保留真实作者、评审和合并记录。
5. **留下合并和验收证据。** 主责在 Issue 或证据索引登记 PR、审批人、被测 SHA、测试结果、GitHub 显示的合并人及合并 SHA。若“合并时同步证据”被选为第二轮干预，第一轮使用现行流程并按预定时间记录基线，第二轮再启用新的合并清单。两轮按同一规则和时间点检查证据完整度，保留基线快照和实际样本。迭代结束由 Mao 更新跟踪 Issue 的 review、retrospective 和待办。最终由 Hao 与 Mao 核对固定提交或 release、老师访问权限及干净目录复现，证据索引区分软件测试 SHA 和后续仅更新文档的提交。
