## 1. 交付目标与范围

V1 的目标是让用户在真实录入的库存上完成“保存库存 → 找可做菜谱 → 查看缺口 → 保存单菜购物清单”，刷新浏览器和重启服务后仍可继续。沿用 V0 界面与纯计算代码，新增 HTTP 服务、SQLite 持久化、服务端校验和可验证的恢复流程。

| 交付项 | V1 必须达到的行为 |
| --- | --- |
| P1 库存 | 新增、查看、编辑、确认删除；保存的是总量；刷新及服务重启不丢数据；保存失败不假报成功 |
| P2 菜谱 | 持久化目录提供配料、数量、单位、步骤；空库存可浏览；详情返回保留筛选和位置 |
| P3 匹配 | 服务端按规范 ID 和单位计算；不足、刚好、富余、缺失及小数正确；不兼容单位明确阻止“现在可做” |
| P4 单菜清单 | 持久保存选择与缺口；重复选择不累加；库存修改后同步更新；不扣减库存；单位无法比较时不给出可采购的部分清单 |
| 运行与交接 | 独立开发/测试数据库、版本化迁移、真实数据库失败测试、备份恢复、第二成员新环境复现、发布与反馈记录 |

主交付采用 **本机受控、单空间运行**。多人身份隔离、HTTPS 和持续托管属于第 12 节的额外发布条件；未通过时仅交付本地版。数据库中提前保留 workspace 归属字段，不能因此宣称已实现多人隔离。

V2 保留多菜合并、已购勾选、每日灵感、热量估算和反馈改进。V1 不增加原生 App、自由文本食材归一、食材识图、在线 AI 推荐、菜谱管理后台或支付。规范食材目录仍为选项录入；新增目录条目通过受控种子数据提交。

## 3. 技术方案与复用边界

沿用 React、Vite、JavaScript ESM、现有 Node 22 运行基线；服务采用 Express，数据库采用 SQLite + better-sqlite3，使用显式 SQL 迁移。新增依赖在实施时核对兼容性并提交锁文件，本计划不虚构已安装版本。

开发时 Vite 仅把 `/api` 代理到本地服务；交付时 Express 同源提供 `dist/` 和 `/api`。浏览器仅通过相对 `/api` 访问服务，数据库文件不在 `public/` 或静态目录中。

配置默认方案：开发前端仍为 `127.0.0.1:5173`，API/交付服务为 `127.0.0.1:3001`，Vite 代理至 3001。服务读取 `HOST`、`PORT`、`DB_PATH`、`NODE_ENV`；DB_PATH 统一解析成绝对路径，默认相对应用根目录而非任意启动目录。提供不含凭据的 `.env.example` 或等价配置样例及跨平台启动脚本；浏览器构建不得注入数据库路径和服务端凭据。

```text
React 页面 / AppProvider
          ↓ HTTP client
Express 路由 → workspace 上下文 → 业务服务 / 共享校验与计算
                                      ↓ 事务
                               SQLite repositories
```

## 4. 数据结构与迁移

数量使用整数百分单位存储：`quantity_minor = quantity × 100`。例如 1.25 g 存 125；2 piece 存 200。piece 必须整件，g/ml 最多两位小数；API 保持 V0 的普通数值表示。数量范围维持 0–1,000,000；转换前拒绝非法精度与非有限值，不通过四舍五入掩盖错误输入。

| 表 | 主键/关键字段 | 不变量 |
| --- | --- | --- |
| `schema_migrations` | version、checksum、applied_at | 版本唯一；已执行迁移内容变更必须报错 |
| `workspaces` | id、initialized、revision、pantry_version、updated_at | 本地由服务选择固定空间；revision 用于写入冲突检查 |
| `ingredients` | id、name、singular | 使用稳定 ID，显示名不参与匹配 |
| `ingredient_units` | ingredient_id、unit | 联合唯一；只允许明确定义的单位 |
| `recipes` | id、title、description、time、image、note、source | 步骤可用独立表存储，不信任请求注入菜谱 |
| `recipe_steps` | recipe_id、position、text | 顺序唯一；目录有可读步骤 |
| `recipe_requirements` | recipe_id、ingredient_id、quantity_minor、unit、position | 同菜同食材唯一；数量有效；关联规范食材/单位 |
| `shopping_lists` | workspace_id、recipe_id、status、pantry_version、catalog_version、updated_at | 每空间最多一个当前单菜清单；状态为 ready/needsShopping/checkUnits |
| `shopping_list_items` | workspace_id、ingredient_id、quantity_minor、unit、position | 只持久化正缺口；与清单处于同一事务 |
| `pantry_items` | workspace_id、ingredient_id、quantity_minor、unit、updated_at | `(workspace_id, ingredient_id)` 唯一；保存覆盖总量 |
| `catalog_metadata` | version | 快照及清单记录使用的目录版本 |

设置外键与有效数量约束，并在每个连接启用外键检查。`pantry_items` 和 `recipe_requirements` 的 `(ingredient_id, unit)` 关联合法单位表；piece 的整数约束同时在服务与数据库中检查。仓储查询必须带 workspace 条件，不接受任意浏览器 workspaceId。

迁移规则：

- 开发库使用如 `var/dev.sqlite` 的持久文件；测试库位于每次运行独立的临时目录；数据库、日志、备份和本地配置均忽略提交。
- `db:migrate` 顺序执行未应用迁移，每个迁移有事务、版本和校验和。空库可建表，旧库可升级，重复执行无变化；未知更高版本直接停止启动。
- 创建数据库文件只由显式初始化/迁移命令完成；普通服务启动要求目标文件存在且 schema 就绪，路径拼错不能静默生成空库。
- `db:seed` 仅补齐受控目录，不重写库存或用户清单。已有目录若要改需求量，必须作为显式目录版本升级，事务中重算全部受影响清单。
- 首次使用可选样例库存或空库存；仅在 `initialized=false` 时允许一次性写入，且与标志更新一起提交。已初始化空间返回首页只提供继续使用，不能再次覆盖真实库存。
- V0 内存数据没有可靠历史导出，不承诺自动迁移；V1 首次使用从新空间开始，明确说明这一变化。
- 迁移前备份；不把破坏性 down migration 作为默认回退。恢复旧兼容应用与其对应的整库备份，再验收。

## 5. HTTP 合同与状态一致性

正常写入响应返回完整权威快照，与 `GET /api/snapshot` 形状相同。前端在成功后一次性替换快照，不自行拼接库存和旧缺口。快照至少包括 `schemaVersion`、`catalogVersion`、`revision`、`pantryVersion`、`initialized`、规范目录、库存、全部匹配、购物选择及其状态。

| 方法与路径 | 请求 | 成功与错误语义 |
| --- | --- | --- |
| `GET /api/health` | 无 | 服务和轻量数据库可读检查通过为 200；不可用为 503；不暴露路径或数据 |
| `GET /api/snapshot` | 无 | 200；在同一读事务中取得一致快照 |
| `POST /api/onboarding` | `{mode:"sample"|"empty", expectedRevision}` | 200；仅未初始化空间可用；再次调用 409，不清空旧数据 |
| `PUT /api/pantry/:ingredientId` | `{quantity, unit, expectedRevision}` | 200；新增或覆盖总量，不接受客户端 shortages/status/workspaceId |
| `DELETE /api/pantry/:ingredientId` | `{expectedRevision}` | 200；经前端确认，删除本空间条目；条目已不存在时不创建副作用 |
| `PUT /api/shopping-selection` | `{recipeId, expectedRevision}` | 200；按当前库存生成/替换单菜清单，重复不累加；新选择单位不兼容时 422，保留旧选择 |
| `DELETE /api/shopping-selection` | `{expectedRevision}` | 200；只清除选择与清单，不改库存 |

预期状态码：400 为 JSON/请求结构错误；404 为未知食材/菜谱；422 为数量、单位或业务校验失败；409 为版本冲突/已完成初始化；503 为数据库忙或存储不可用；未预期错误为 500。错误统一为 `{error:{code,message,field?,requestId}}`，不返回堆栈、SQL 或磁盘路径。多人模式另有 401/403。

单菜快照沿用 V0 的 `shoppingRecipeId`、`shopping` 等业务字段以减少页面改动；V0 的 `sessionId` 重置机制不再承担持久化初始化职责。未初始化快照也包含目录与空库存，允许浏览菜谱；第一次普通写入同事务设 `initialized=true`，避免后来样例入口覆盖其数据。

### 每次库存写入的事务

1. 获取服务端 workspace；开启写事务，核对 `expectedRevision`。
2. 校验参数与目录，新增/覆盖/删除库存，递增库存版本。
3. 若已选菜谱存在，读取新库存并重新计算。全部同单位时替换清单条目；不兼容时将清单状态改为 `checkUnits` 并清除可采购条目，保留所选菜谱。
4. 更新 workspace revision，读取本事务的完整快照；提交成功后才发 200。
5. 任意步骤失败回滚库存、选择、条目及版本；不返回伪造的成功快照。

选菜写入同样在事务内读取最新库存、计算并替换选择和条目。GET 对照清单的库存/目录版本，发现不一致时不能把旧条目标为“最新”；返回需同步错误并由受控修复流程重建，不静默显示旧采购量。

V1 不提供通用 reset API。测试使用临时库，演示重置另开一次性演示数据库，不向真实库存提供 V0 式全局清空按钮。

### 并发、重试与失败

- 所有业务写入带已读 revision；事务内比较。两个标签页持有同一旧版本时，一个成功，另一个返回 409；后者保留草稿并提示重新加载/核对后保存，不能覆盖最新数据。
- 库存 PUT 是设置总量，购物 PUT 是替换选择，均不做累加。重发旧 revision 可返回 409，重新读取并核对目标状态后再决定是否重试。
- 网络超时可能发生在提交之后。UI 显示“暂未确认保存结果”，先 GET 核对；GET 也失败时保留草稿且不提示成功，恢复后再同步。不能将所有超时都写成“数据库未保存”。
- 初始 GET 失败显示可重试错误页；写入失败保留原快照和输入；不先扣库存，不自动回退 mock，不允许无限重试。
- 页面重新获得焦点或从失联恢复时重新获取快照；若 revision 有变化提示数据已更新。V1 不承诺 WebSocket 实时推送，跨标签写入由版本冲突保护。

## 6. 计算、菜谱与界面细节

- 缺口 = `max(required − available, 0)`；缺失库存为零，省略零缺口，保持菜谱顺序。整数百分单位计算后转换显示，避免小数残差。
- V1 仅支持已定义的同单位比较，继续使用 piece/g/ml。piece 与 g、g 与 ml 均不猜测换算；kg/l 等新单位留给后续显式转换规则与验收。
- 所有必需食材都满足才可做。若部分单位无法比较，整道菜和清单为 `checkUnits`，不能将其余可比项当成完整采购清单。
- 同食材同空间只有一个库存总量；0 为合法数值，删除由独立动作表达；未知 ID、重复需求和非法目录数据都不能进入服务计算。
- 冻结原有两道演示菜谱作为回归夹具；补充至少一道经核验的多食材菜谱，使浏览器流程实际覆盖多项需求。按 2026-11-06 的追加要求，目录扩充为最多 20 道菜（含两道回归样例），补充对应规范食材并生成配图；仍采用规范目录选项，不增加自由输入归一。记录内容来源、数量、步骤及许可，图片缺失时使用已有样式占位。
- 保留筛选、滚动、键盘导航、确认框、375px 布局。首页和页头改为持久保存语义；移除“刷新会清空”文案以及会覆盖数据的样例/重置交互。
- 区分“尚未选择菜谱”“有缺口”“无需购买”“单位待核对”“正在加载”“服务不可用”“版本冲突”。状态需有文字，不能只靠颜色。

## 10. 发布、备份与回退

本地交付流程：完成源代码评审 → 所有核心验收通过 → 合入 main 并确认该 SHA 的 CI → 打包源代码/锁文件/迁移/手册与证据 → 从新目录安装、迁移、初始化目录、构建、启动 → 独立成员复现 → 标识实际发布版本与限制。发布包不包含开发者数据库、凭据或 node_modules。

计划脚本包括 `dev`（前后端协同启动，跨平台）、`build`、`start`、`db:migrate`、`db:seed`、`db:backup`、`db:restore`。具体命令、配置字段、端口与退出码由 V1-RUNBOOK 在实现后给出，当前不能将这些入口当成已存在。

本地运行应在缺失目录、配置错误、端口占用、不可写数据库及不兼容 schema 时明确失败，不静默新建另一个文件造成“数据丢失”。启动记录数据库标识与迁移版本，日志避免真实库存明细和敏感凭据。

备份优先在停止服务且确认连接关闭后复制完整一致数据库；如需在线备份，必须使用数据库支持的一致性备份方式并验证。不能只复制活动数据库主文件而遗漏日志状态。备份写入独立目录，记录版本、时间、校验值，不覆盖唯一旧备份；发布/迁移前必备份，保留最近至少两份本地有效备份。

恢复必须停止服务，保留故障库副本，将备份恢复到新路径，先检查完整性及 schema，再启动兼容应用并核对库存、选择和缺口。A16 证明恢复流程真实可用。共享试运行另需离机备份和经确认的保留期。

## 12. 有条件的多人共享试运行

这是本地 V1 之后单独估时和验收的扩展包，不包含在上述 64 人时之内。需要共享试用时，Hao 与 Mao 先明确维护人、主机和预算，再安排实施，不靠延长五日计划里的单人固定 workspace 模式上线。
